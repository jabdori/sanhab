# 산합(SanHab)

이름이 다른 대리점이 사실은 관련된 곳일 때, 판매장려금을 합산해 승인권자를 정하고 등록 정보가 바뀌면 지난 승인까지 다시 검토하게 하는 업무 시스템입니다. 기업 업무 과제를 AI로 푸는 대회에서 받은 업무(관련 거래처와 판매장려금 지급)로 2026년 11월에 만들었습니다.

- 시연 영상(5분 44초): https://youtu.be/UvKgy-QlBrM
- 데이터: 대회가 제공한 가상 기업 자료

## 하는 일

- **관련 거래처 그룹과 승인권자**: 대리점, 대표자, 주소, 정산계좌를 그래프로 이어 둘 이상 일치하는 대리점을 한 그룹으로 계산합니다. 그룹과 귀속월 단위로 지급을 합산하고, 한 달 200만 원을 넘으면 승인권자를 영업임원으로 올립니다.
- **정보가 바뀌었을 때**: 등록 정보 변경을 변경일과 인지일로 받아 그룹과 합산을 다시 계산합니다. 끝난 승인은 고치지 않고 재검토로 표시해 영업임원 추인과 내부 감시 종결로 닫고, 지급을 기다리던 건은 재심사로 멈춥니다. 어느 작업에서든 경위를 따라 처음 사건까지 거슬러 갈 수 있습니다.
- **정황과 AI 보고**: 계좌 공유, 대표자 동명, 한도 근접 반복, 대사 불일치 같은 정황을 코드가 찾아 내부 감시에 올립니다. AI는 근거를 사실, 추정, 미확인으로 나눈 보고와 소명 요청서 초안을 씁니다.
- **소명 서류**: 업스테이지 글자 인식으로 읽고 AI가 값을 정리하면, 코드가 등록 정보와 비교합니다(예: 임대차계약서의 호실).
- **대사**: 은행 회신의 금액과 계좌를 승인 금액, 지급일의 등록 계좌와 맞춰 봅니다.

## AI가 맡는 일과 막아 둔 일

- AI는 정황 보고, 소명 요청서 초안, 서류 값 정리, 대화 답을 맡습니다.
- 관련자 여부, 합산, 승인권자는 코드가 계산하고, AI는 이 값을 만들거나 고치지 못하게 DB 권한으로 막았습니다. AI가 근거로 가리킨 기록이 실제로 있는지는 코드가 검사합니다.
- 대화에서 조치를 요청해도 AI는 실행하지 않고 조치 카드만 냅니다. 실행은 권한이 있는 사람이 누릅니다.
- 읽기 범위도 역할별로 DB가 강제하고, 대화 AI는 묻는 사람의 권한 안에서만 읽습니다.

## 구성

| 부분 | 사용 |
|---|---|
| 백엔드 | Rust, axum |
| 화면 | React 19, Tailwind CSS 4, jotai (빌드 결과를 실행 파일에 포함) |
| DB | SurrealDB 4 (그래프 관계, 버전 기록으로 시점 조회) |
| 글자 인식 | 업스테이지 API (`UPSTAGE_MODEL`로 모델 변경) |
| LLM | OpenAI API (`OPENAI_MODEL`로 모델 변경) |
| 배포 | Docker Compose (AXHub) |

## 실행

대회가 제공한 자료(`01_참가자_배포용/`)는 대회 약관에 따라 이 저장소에 넣지 않았습니다. 앱은 빌드할 때 그중 네 파일(대리점, 지급, 회수 기록과 승인 규정)을 실행 파일에 넣으므로, 자료가 있으면 같은 경로에 두고 실행합니다.

```sh
cp .env.example .env                  # 값 채우기
docker compose -p axw up -d --build   # http://localhost:3000
```
