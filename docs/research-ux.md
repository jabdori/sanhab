# 우수 사례 리서치 (UX)

조사일 2026-11-11. 공식 도움말·디자인 시스템 문서·UX 연구 글을 직접 읽고 정리했다.
표의 `확인함`은 인용한 페이지에서 직접 읽은 내용, `추정`은 검색 결과 요약·스크린샷·일반 지식에서 끌어낸 내용이다.

## 요약

- 승인 도구는 공통으로 "내가 다음 승인자인 건만" 모아 보여 주고, 반려에는 사유를 받고, 승인 이력은 건마다 따로 남긴다. 금액·거래처·계좌가 바뀌면 승인을 처음부터 다시 태우는 규칙(Ramp)은 우리 "재심사 대기"와 같은 생각이다.
- 정황 검토 도구(Unit21, Hummingbird)는 "확인 목록을 다 채워야 종결 버튼이 나타난다"는 방식으로 대충 넘기는 것을 막는다. 결론은 자유 서술이 아니라 정해진 분류 버튼으로 남긴다.
- 문서 대조 도구(Rossum, Docsumo)는 값마다 "누가 확인했나"를 표시한다. AI가 확인한 값, 사람이 확인한 값, 아직 아무도 확인하지 않은 값을 구분하고, 사람은 확인 안 된 값부터 본다. 값을 누르면 원문 위치가 강조된다.
- AI 결과 표시는 "숫자 확신도"보다 "높음/중간/낮음 + 각 단계에서 사람이 할 일"이 안전하다(Google PAIR). 출처는 주장 바로 옆에 붙이고 원문의 해당 위치로 연결해야 한다. 사람들은 출처 링크를 거의 누르지 않는다(NN/g).
- 설명을 더 붙이는 것만으로는 AI를 그대로 따르는 버릇이 줄지 않는다. 사람이 먼저 판단하게 하는 등 "생각을 강제하는 장치"가 더 효과적이지만 사용자는 그 방식을 덜 좋아한다(Harvard 연구).
- 관계 그림은 전체를 다 그리면 엉킨 실뭉치가 된다. 한 대상의 이웃만 보여 주고, 필요할 때 펼치고, 이웃이 많으면 묶는다. "왜 연결됐나"는 선에 직접 적는다.
- 상태 표시는 색만으로 구분하지 않는다. 아이콘+색+글자를 함께 쓰고, 종류는 5~6개를 넘기지 않는다(Carbon).
- 근거가 얇았던 갈래: 한국 전자결재, Sardine·ComplyAdvantage·Alloy·Feedzai, Onfido·Nanonets·Google Document AI, 출처 등급 표시의 업계 표준, 역할 전환. 맨 아래 "확인하지 못한 것"에 적었다.

**가져올 것**
- 내 할 일: "내 차례인 건"과 "다른 사람 차례라 기다리는 건"을 탭으로 나눈다. 한국 전자결재의 "대기/예정" 구분과 같아 익숙하다.
- 심사: 반려·보류에는 사유를 받고, 사유는 고쳐서 다시 올리는 사람에게 그대로 보인다.
- 심사: 건마다 승인 이력을 두고, 적용된 규정 조항·규칙 버전을 그 시점 값으로 고정해 보여 준다.
- 지급: 승인 뒤 금액·계좌·대상이 바뀌면 "재심사 대기"로 돌리고, 무엇이 바뀌어서 돌아왔는지 한 줄로 적는다.
- 지급: 되돌리기는 "실제 지급 처리 전까지만" 가능하다는 경계를 화면에 적는다.

**피할 것**
- 내 할 일: 금액이 크거나 정황이 붙은 건까지 일괄 승인에 섞이게 하는 것. 일괄 처리는 정황 없는 건으로 제한한다.
- 심사: AI 권고를 승인 버튼과 같은 무게로 놓거나, 권고대로 미리 선택해 두는 것.
- 규정: 규칙을 바꿨을 때 진행 중인 건의 승인자가 조용히 바뀌는 것.

**가져올 것**
- 정황: 맨 위 요약 한 줄(무슨 신호, 누구, 얼마, 기한, 현재 상태) → 근거 → AI 조사 보고서 → 조치 순서로 놓는다.
- 정황: "종결"과 "AI 보고서 채택"은 확인 목록(예: 근거 원문을 열어 봤는가)을 채운 뒤에만 눌리게 한다.
- 정황: 종결 사유는 고를 수 있는 분류 + 짧은 메모로 받는다. 나중에 "왜 종결했나"를 셀 수 있다.
- 대리점: 같은 대리점·같은 묶음의 정황은 한 페이지에 모아 보여 준다.
- 정황·소명: 조치 버튼은 화면 오른쪽 같은 자리에 고정한다.

**피할 것**
- 정황: 같은 대상에 같은 종류의 정황을 여러 건 따로 띄우는 것.
- 정황: 모든 조치에 확인 창을 띄우는 것. 되돌리기 어려운 조치에만 쓴다.
- 내 할 일: 정황을 심각도 표시 없이 시간순으로만 쌓는 것.

- 소명: 사람이 한 번도 보지 않은 값이 있는데도 "수용"이 눌리는 것.

## 화면 전반

**표와 대기열**
- 표가 지원할 일은 네 가지다. 조건에 맞는 건 찾기, 비교하기, 한 건 보기·고치기, 조치하기. 출처: NN/g https://www.nngroup.com/articles/data-tables/ (확인함)
- 첫 열은 자동 생성 번호가 아니라 사람이 읽을 수 있는 이름으로 한다. 열 순서는 중요도 순으로 한다. (같은 글, 확인함)
- 필터가 켜져 있으면 "지금 걸러진 결과를 보고 있다"는 표시가 분명해야 한다. (같은 글, 확인함)
- 표가 화면보다 크면 머리글 행과 첫 열을 고정한다. 줄무늬나 마우스 올림 강조로 줄을 놓치지 않게 한다. (같은 글, 확인함)
- 한 건을 자세히 볼 때 화면을 덮는 창은 다른 줄을 가려 참고할 수 없게 만든다. 표를 가리지 않는 옆 패널이 낫다. (같은 글, 확인함)
- 줄마다 조치 버튼이 3개 이상이면 좁아서 누르기 어렵거나 숨겨져 찾기 어렵다. 여러 건 조치는 체크박스 + 표 위 버튼으로 한다. (같은 글, 확인함)
- 알림함에 "주의가 필요한 것" 탭을 따로 두고, 키보드(J/K 이동, H 미루기)로 빠르게 넘긴다. 출처: Linear https://linear.app/docs/inbox (확인함)

**상태 표시 낱말**
- 상태 표시는 아이콘·모양·색·글자를 함께 쓴다. 색만으로 구분하지 않는다. 출처: Carbon https://carbondesignsystem.com/patterns/status-indicator-pattern/ (확인함. 같은 페이지 안에서 "최소 3가지"와 "최소 2가지"가 섞여 있다)
- 상태 종류가 5~6개를 넘으면 사용자가 버거워한다. (같은 페이지, 확인함)
- "상태"(지금 어떤 단계인가)와 "심각도"(얼마나 중대한가)는 다른 것이다. 아이콘을 섞어 쓰지 않는다. 출처: PatternFly https://www.patternfly.org/patterns/status-and-severity (확인함)
- 우리 화면에는 서로 다른 축이 셋 있다. 처리 상태(대기·보류·승인·반려·재심사 대기), 정황 심각도, 출처 등급. 축마다 모양을 다르게 해서 한 줄에 같이 있어도 헷갈리지 않게 한다. (추정, 위 두 원칙에서 끌어냄)
- 검토 결과를 "의견만 / 승인 / 수정 요청" 세 가지로 나눈다. 출처: GitHub 문서(위 E 표, 확인함). 우리 "승인 / 보류 / 반려"와 같은 구조다.

**사유를 받는 확인 창**
- 확인 창은 결과가 무겁고 되돌릴 수 없는 조치에만 쓴다. 일상 조치에 쓰면 습관적으로 넘기게 된다. 출처: NN/g https://www.nngroup.com/articles/confirmation-dialog/ (확인함)
- "정말 하시겠습니까?"라고 묻지 않는다. 무슨 일이 생기는지를 사용자 말로 적는다. 버튼은 예/아니오가 아니라 결과를 적는다(예: "반려하고 돌려보내기" / "취소"). (같은 글, 확인함)
- 가능하면 확인 창 대신 되돌리기를 준다. (같은 글, 확인함)
- 반려 사유는 필수로, 올린 사람에게 전달한다. 출처: Ramp Bill Pay 문서(위 A 표, 확인함)

**출처 등급과 확신 표시**
- 출처(provenance)는 "어떤 것(entity)이, 어떤 활동(activity)으로, 누구(agent)의 책임 아래 생겼나"의 기록이다. 출처: W3C https://www.w3.org/TR/prov-primer/ (확인함)
- 우리 다섯 등급(원자료 / 계산 / 가정 / AI 작성 / 시연 입력)은 이 중 "누가·무엇으로 만들었나"에 해당한다. 등급 표지를 누르면 "어디서 왔나"(원자료 위치, 계산식, 가정 항목, AI 실행 기록)가 열리게 하면 Carbon의 "AI 표지 → 설명 팝오버" 구조와 같다. (추정, Carbon for AI와 W3C 정의에서 끌어냄)
- 값마다 확인 출처를 표시하고 눌러서 상세를 보는 실제 예는 Rossum(회색/초록 체크, "항목 상세")이다. (확인함, C 표)
- 다섯 등급을 색으로만 나누지 않는다. 짧은 글자 표지를 붙인다. (추정, Carbon 상태 표시 원칙에서 끌어냄)

**역할 전환**
- 다른 역할로 보는 중에는 화면 맨 위에 지울 수 없는 색 띠를 두고, 지금 누구·어떤 역할로 보는지와 나가기 버튼을 넣는다. 여러 제품의 도움말 검색 결과에서 공통으로 보였으나 원문을 직접 읽은 것은 없다. (추정)
- 역할을 바꿔서 한 조치도 실제 사용자 이름으로 기록한다. (추정, 같은 검색 결과)
- 본인이 올린 건을 본인이 승인하지 못하게 하는 직무 분리 설정은 Ramp에서 확인했다. 시연 도구로 역할을 바꿔 가며 같은 건을 올리고 승인하는 장면에서는 "시연 입력" 등급으로 표시해 실제 통제와 구분해야 한다. (앞 문장 확인함, 뒤 문장 추정)

## 화면별 정리

**내 할 일**
- "내 차례"와 "기다리는 중"을 탭으로 나눈다. (A: Ramp, NAVER WORKS)
- 종류별 건수와 기한 지난 건수를 맨 위에 둔다. (C: Hyperscience)
- 첫 열은 사람이 읽는 이름, 필터가 켜져 있으면 표시한다. (화면 전반: NN/g)
- 묶는 단위를 정한다. 심사는 승인 단위로, 정황은 대리점·묶음 단위로 모은다. (B: Sardine)
- 일괄 승인은 정황 없는 건으로 제한하고 확인을 한 번 거친다. (A: Ramp)

**심사**
- 묶음 구성·합산 금액·필요 승인자를 맨 위에 두고, "왜 묶였나"는 선에 공유 식별자를 적은 작은 그림으로 보여 준다. (E: Cambridge Intelligence, Unit21)
- 적용 조항과 규칙 버전은 그 시점 값으로 고정해 보여 주고, 건별 승인 이력을 둔다. (A: Ramp)
- 반려·보류는 사유 필수, 확인 창의 버튼에는 결과를 적는다. (A: Ramp, 화면 전반: NN/g)
- 붙어 있는 정황은 "검토 권고" 수준으로 보여 주고 승인 버튼과 무게를 다르게 한다. (A·D: Ramp)
- 조치 버튼은 오른쪽에 고정한다. (B: Unit21)

**대리점**
- 관계 그림은 1단계 이웃만, 눌러서 펼치기, 이웃이 많으면 "+숫자"로 묶는다. (E: Linkurious, Neo4j Bloom, dbt)
- 그림과 같은 내용을 연결 유형별 목록으로도 둔다. (E: Palantir, Unit21)
- 이 대리점의 정황을 한 페이지에 모은다. (B: Sardine)
- 등록 정보의 값마다 출처 등급 표지를 붙인다. (화면 전반)

**정황**
- 요약 → 근거 → AI 보고서 → 조치 순서로 놓고, 조치는 오른쪽에 고정한다. (B: Unit21)
- 보고서 네 부분을 모양으로 구분하고, 사실 문장마다 원문 위치로 연결한다. (D: NN/g, PAIR; C: Docsumo)
- 확신은 숫자 대신 범주 + 할 일로 보여 준다. "확인하지 못한 것"은 접지 않는다. (D: PAIR)
- 채택·종결 전에 확인 목록을 채우게 하고, 금액이 큰 건은 검토자 판단을 먼저 받는다. (B: Unit21; D: Buçinca 외)
- 종결 사유는 분류 + 메모로 받는다. (B: Unit21, Sardine)

**소명**
- 원본 이미지와 값을 나란히 두고, 값과 위치가 서로 강조되게 한다. (C: Docsumo)
- 값마다 "원본에서 읽음 / AI 정리 / 사람 확인"을 표시하고, 확인 안 된 값부터 본다. (C: Rossum)
- 멈춘 이유(불일치, 낮은 확신, 못 찾음)를 맨 위에 모은다. (C: Rossum)
- 사람이 고친 값은 표지가 바뀌고 AI 값으로 되돌릴 수 있다. (D: Carbon for AI)
- "수용 / 기각 / 증빙 부족"은 같은 무게로 놓고, 기각·증빙 부족에는 사유를 받는다. (A: Ramp; C: Persona)

**지급**
- 승인 뒤 금액·계좌·대상이 바뀌면 "재심사 대기"로 돌리고 바뀐 항목을 적는다. (A: Ramp)
- 되돌릴 수 있는 시점의 경계(지급 처리 전까지)를 화면에 적는다. (A: Ramp)
- 대사 결과는 "일치 / 불일치 / 대상 없음"처럼 적은 수의 상태로, 아이콘+색+글자로 표시한다. (화면 전반: Carbon)
- 건마다 감사 이력을 둔다. (E: Unit21)

**왜 생겼나**
- 원인은 왼쪽, 결과는 오른쪽에 놓고 방향을 고정한다. (E: dbt, Neo4j Bloom)
- 처음에는 한 단계만 보이고 눌러서 이어 간다. "이 점 기준으로 다시 보기"를 둔다. (E: dbt)
- 관계보다 순서가 중요하므로 시간 축을 함께 둔다. (E: Cambridge Intelligence)
- 같은 그림에서 색칠 기준(상태, 출처 등급)만 바꿔 본다. (E: dbt 렌즈)

**규정**
- 규칙 버전을 바꾸면 새 건부터 적용하고, 지난 건은 당시 버전을 그대로 보여 준다. (A: Ramp)
- 한도 가정 실험은 "지금 규칙"과 "바꾼 규칙"의 결과를 나란히 놓고, 결과에 "가정" 등급을 붙인다. (화면 전반: 출처 등급. 한도 가정 실험 화면 자체의 선례는 찾지 못함)
- AI가 하는 일·하지 않는 일, 사람 검토로 보내는 기준을 적는다. (D: HAX G1·G2; C: AWS, Rossum)
- 가정 목록의 각 항목은 그 가정이 쓰인 화면으로 연결한다. (D: PAIR의 "근거 자료 출처" 원칙에서 끌어냄, 추정)

**시연 도구**
- 역할을 바꾼 동안에는 맨 위에 지울 수 없는 띠로 현재 역할을 보여 준다. (화면 전반: 역할 전환, 추정)
- 날짜를 앞당겼거나 시연으로 넣은 값은 모든 화면에서 "시연 입력" 등급으로 보인다. (화면 전반: 출처 등급)
- 초기화는 되돌릴 수 없으므로 확인 창을 쓰고, 버튼에 결과를 적는다. (화면 전반: NN/g)

## 확인하지 못한 것

- **Unit21의 판정(disposition)·감사 이력·관계 표(Link Analysis)·AI Agent 문서**: 일부 페이지가 로그인으로 넘어가 읽지 못했다. 판정 관련 내용은 검색 결과 요약에만 의존했다. "Managing an Alert", "How to resolve an Alert", "Network Analysis" 세 페이지는 직접 읽었다.
- **SAP Fiori 승인 앱 가이드**: 주소가 다른 페이지로 넘어가 읽지 못했다. "결정별 의견 필수 설정"은 검색 결과 요약이다.
- **SAP Concur, Coupa(승인 기능), Airbase**: 찾아보지 못했다.
- **한국 전자결재**: NAVER WORKS 한 곳만 봤고, 승인 문서 페이지는 본문 일부만 읽혔다. 반려 사유가 필수인지는 문서에 없었다. 다우오피스 안내서(PDF)는 열지 않았다. 다른 그룹웨어는 못 봤다.
- **Sardine**: 대기열 문서 한 장만 읽었다. 정황 상세 화면과 기기 관계 그림은 못 찾았다.
- **ComplyAdvantage, Alloy, Feedzai**: 화면 구성을 설명한 공개 문서를 찾지 못했다.
- **Hummingbird의 AI 서술 기능, Persona의 Case Review Agents**: 홍보 글과 검색 요약으로만 봤다. 사람이 AI 초안을 어떻게 수용·수정하는지는 확인하지 못했다.
- **Onfido, Nanonets, Google Document AI 사람 검토, Hyperscience 검토 화면 자체**: 읽지 못했다. Hyperscience는 작업 목록 페이지만 봤다.
- **AWS Textract + A2I 검토 화면**: 블로그 글이 중간에 잘려 화면 배치 설명은 못 읽었다. 문서에 따르면 이 서비스는 신규 고객에게 닫혀 있다.
- **"왼쪽 값 / 오른쪽 원본" 배치**: 스크린샷과 검색 요약에서는 흔했지만, 배치를 글로 명시한 공식 문서는 찾지 못했다. Docsumo 문서는 "원본이 위"와 "원본 옆"을 함께 적어 스스로도 엇갈린다.
- **Maltego, Atlan, Palantir의 이력 보기**: 못 봤다. Palantir는 연결 대상 목록만 확인했다.
- **GitHub·Linear의 활동 타임라인 세부**: GitHub는 "타임라인에 검토가 쌓인다"는 한 줄만, Linear는 알림함만 확인했다.
- **원인-결과 사슬 그림(왜 생겼나)의 직접 선례**: 업무 도구에서 "한 사건이 만든 할 일과 상태 변화"를 그림으로 보여 주는 예는 찾지 못했다. 데이터 계보 그림(dbt)에서 빌려 왔다.
- **출처 등급을 화면에 표시하는 업계 표준**: 찾지 못했다. W3C 정의, Carbon의 AI 표지, Rossum의 확인 출처 표시를 조합한 것이다.
- **역할 전환 표시**: 원문을 직접 읽은 자료가 없다. ServiceNow 문서는 기능을 켜는 설정만 다뤘고, 다른 한 곳은 페이지가 없었다.
- **한도 가정 실험(what-if) 화면**: 따로 조사하지 못했다.
- **Carbon 상태 표시 문서의 "최소 요소 수"**: 같은 페이지에 3가지와 2가지가 함께 적혀 있어 어느 쪽이 기준인지 확정하지 못했다.
