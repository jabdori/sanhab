# 서비스 기획 (W07)

누가 어느 화면에서 무엇을 보고 무엇을 하는가. 근거는 `docs/graph-spec.md`와 `docs/user-scenarios.md`. 화면을 합치거나 나누는 것은 UX 기획에서 조정한다.

## 확정된 결정
- **S1. 첫 화면은 "내 할 일".** 로그인하면 내 역할에 온 작업 목록이 먼저 나온다. 현황판은 두지 않거나 보조로 둔다. 과제문이 지표·차트만으로는 완료로 보지 않는다고 했다.
- **S2. 접속 패스워드 하나, 그 뒤 역할 선택.** 앱 주소가 인터넷에 공개되어 있으므로 처음 들어올 때 공용 접속 패스워드를 한 번 받는다. 통과하면 역할을 골라 들어오고 화면 위에서 역할을 바꿀 수 있다(역할별 비밀번호는 없다). 역할별 권한은 그대로 강제한다. 패스워드와 역할 전환 방법은 제출 화면의 "심사위원 실행 안내"(선택, 최대 2,000자, 로그인이 필요한 앱은 테스트 계정 필수)에 적는다. 설계 설명에 "실제 운영에서는 계정 인증을 붙인다"고 적는다.
- **S3. 그래프를 두 곳에서 그림으로 보여준다.** 대리점 화면(관련자가 어떤 사람·주소·계좌로 이어져 있는지)과 왜 생겼나 화면(사건에서 작업까지의 사슬). 전체 대리점을 한 장에 그리는 화면은 만들지 않는다.
- **S4. 화면 기술.** 최신 React(19.x) + Base UI(`@base-ui/react` 1.x, 모양이 없는 부품 라이브러리) + jotai(상태 관리). Base UI는 동작과 접근성만 제공하므로 색·글자·간격은 모두 우리 디자인 기준 문서에서 정한다. 겉모습은 Tailwind CSS(4.x)로 입히고, 색·간격의 기준값을 한 파일에 정의해 그 값만 쓴다. 표는 HTML 표에 직접 모양을 입히고 관계 그림은 따로 그린다(Base UI에 없음). 정적 파일로 빌드해 서버 실행 파일에 포함한다. 배포 구성(컨테이너 2개)은 그대로다.
- **S5. 데스크톱 화면이 기준.** 휴대폰에서는 깨지지 않을 정도로만 맞춘다.
- **S6. 화면의 인상.** 조용하고 밀도 있는 업무 도구. 흰 바탕에 표와 글자가 중심이고 색은 상태를 알릴 때만 쓴다. 그림은 대리점·왜 생겼나 두 곳에서만 쓴다.
- **S7. 디자인 하네스(이 프로젝트 전용).** 화면을 만들 때마다 같은 기준으로 만들고 같은 기준으로 검사하게 하는 장치.

| 구성 요소 | 내용 |
|---|---|
| 디자인 기준 문서 | 색, 글자, 간격, 상태 표시의 규칙 |
| 부품 목록 | 표, 상태 표지, 사유 입력 창, 출처 등급 표시 등 공통 부품과 사용 규칙 |
| 문구 기준 | `GLOSSARY.md`의 말을 화면에서도 그대로 쓰게 하는 규칙 |
| 출처 대응 문서 | 화면별로 어떤 요소가 어느 사례(리서치)에서 왔는지 |
| 검사 절차 | 구현한 쪽과 다른 별도의 에이전트가 agent-browser로 화면을 실제로 띄워 눈으로 검수한다. 기준 문서·시나리오와 대조 |
- **S8. 공개 주소에서 AI 호출 요금 보호.** S2의 접속 패스워드로 막는다. 패스워드 없이는 어떤 자료도, AI 호출도 열리지 않는다. 같은 입력의 AI 결과는 저장해 두고 다시 호출하지 않는다. 두 서비스의 관리 화면에서 월 사용 한도를 함께 건다. 앱 안의 하루 호출 상한은 두지 않는다(패스워드로 충분).

| 화면 | 보여주는 것 | 할 수 있는 일 | 주로 쓰는 역할 |
|---|---|---|---|
| 내 할 일 | 내 역할에 온 작업 목록 | 작업을 열어 처리 | 전원 |

| 대리점 | 등록 정보, 관련자와 그 근거(그림), 지급 이력, 걸린 정황과 소명 | 등록 정보 변경 입력(실제 변경일) | 영업지원 |

| 소명 | 서류 원본, 읽은 조각, AI가 정리한 값, 비교 결과 | 서류 올리기, 인정, 불인정, 증빙 부족 | 영업지원, 내부 감시 |
| 지급 | 지급할 건, 재심사 대기 표시, 대사 결과 | 지급 완료, 은행 회신 입력 | 회계·자금 |
| 왜 생겼나 | 어떤 작업이나 상태에서 처음 사건까지의 사슬(그림) | 조회만 | 전원 |
| 규정 | 조항, 규칙 버전, 가정 목록, 한도 바꿔 보기 | 가상 적용 | 영업임원, 내부 감시 |
| 시연 도구 | 현재 날짜, 역할 | 역할 바꾸기, 날짜 넘기기, 초기화 | 시연자, 심사위원 |

## 시나리오가 거치는 화면
- 1 (전결): 내 할 일 → 심사 → (회계) 내 할 일 → 지급
- 2 (합산, 임원): 내 할 일 → 심사
- 3 (과거 재검토): 내 할 일 → 심사(사후 승인) → (내부 감시) 내 할 일 → 심사 확인
- 4 (주소 이전): 대리점 → (각 역할) 내 할 일 → 정황, 심사, 지급 → 왜 생겼나
- 5 (보류와 소명): 심사 → 정황 → 소명 → 심사
- 6 (갈라져도 상신): 소명 → 심사
- 7 (반려): 심사 → (영업지원) 내 할 일
- 8 (한도 바꿔 보기): 규정

## UX 기획에서 확정된 결정
화면에 보이는 낱말은 `docs/design/copy.md`를 따른다(이름표는 명사 한 단어). 아래에서 따옴표 안의 말이 화면 표기다.

- **U1. 관계 그림은 사람·주소·계좌를 점으로 그린다.** 저장된 그래프와 같은 모양이고, "같은 점을 두 개 이상 함께 가리키면 관련자"가 그림에서 읽힌다. 그림은 대리점 두세 곳 규모라 엉키지 않는다. 같은 내용을 표로도 둔다.
- **U2. AI 의견은 접어 둔다.** 조사 보고의 "사실", "추정", "미확인"은 바로 보인다. 임원 상신 대상인 정황에서만 내부 감시가 자기 판단을 먼저 고른 뒤 "의견"이 열린다. 나머지 정황에서는 눌러서 연다.
- **U3. 사유는 분류를 고르고 메모는 선택.** 사유가 필수인 결정에서는 분류 선택이 필수다. "기타"를 고르면 메모가 필수다.
- **U4. 일괄 승인.** 정황이 없고 전결 대상인 건만 여러 개를 골라 한 번에 승인한다. 확인 창을 한 번 거친다. 정황이 걸렸거나 임원 승인 대상인 건은 고를 수 없다.
- **U5. "작업" 화면은 두 갈래.** "담당"(지금 내가 처리할 것)과 "진행"(내가 관여했지만 다른 역할의 차례인 것).
- **U6. 표시는 세 종류, 모양을 달리한다.** 처리 상태는 색이 있는 알약 모양 표지 + 글자, 덧붙는 표시("재검토", "정황", "정산" 등)는 아이콘 + 글자, 출처 등급은 작은 테두리 글자(누르면 어디서 왔는지 열림). 색만으로 구분하지 않는다. 색은 디자인 기준 문서에서 정한다.
- **U7. 시연 도구는 화면 위 띠.** 현재 역할, 현재 날짜, "역할", "날짜", "초기화"를 항상 보이게 둔다. 별도 화면을 두지 않는다. 화면은 여덟 개: 작업 / 심사 / 대리점 / 정황 / 소명 / 지급 / 경위 / 규정.
- **U8. 전체 틀: 왼쪽은 고르는 곳, 가운데는 사실, 오른쪽은 판단.** 왼쪽 메뉴는 작업·대리점·규정 셋. 심사·정황·소명·지급은 "작업" 목록에서 고르면 열린다. 가운데에는 원본과 코드 계산만 놓이고 AI가 쓴 글은 들어가지 않는다. 오른쪽에는 조치 → 사유 → 보고 → 경위 → 이력이 모든 상세에서 같은 순서로 놓이고, 해당 없는 칸은 "없음"으로 자리를 지킨다. 화면별 배치는 `docs/ux-plan.md`.
- **U9. 색.** 바탕·글자·선은 흰색과 회색. 누를 수 있는 것은 남색(이 색은 여기에만). 대기 회색, 승인·인정·일치 녹색, 보류·보완 황색, 반려·불인정·불일치 적색, 재심사 보라색. 덧붙는 표시(재검토, 정황, 정산 등)는 색 없이 아이콘과 글자. AI가 쓴 것에는 색을 쓰지 않고 "AI" 테두리 글자만.
- **U10. 글꼴.** Pretendard. 파일을 앱에 함께 넣는다. 금액과 계좌번호는 고정폭 숫자.
- **U11. 전역 대화 칸.** 오른쪽 끝에 접어 둔다. 펼치면 목록이 접히고 사실·판단은 그대로 보인다. 어느 화면에서든 같은 자리. 화면 표기는 "대화", 머리에 "임시".
- **U12. 보고와 대화의 구분.** 보고는 기록(그래프에 남고, 사실은 기록을 가리키기만 하며, 채택·불채택 대상이고, 경위에 나타난다). 대화는 임시(남지 않고, AI가 글로 답하며 답 아래에 조회한 기록 목록을 코드가 붙이고, 판단의 근거로 남지 않는다). 대화의 내용을 판단에 쓰려면 "보고로 남기기"를 거쳐 검증을 통과해야 한다.
- **U13. 대화가 할 수 있는 일.** DB를 읽는 도구로 조회하고 설명한다. "승인해도 되나" 같은 질문에는 사실과 규정을 답하고 판정 의견은 내지 않는다. 사람이 "~ 사유로 승인해/반려해"라고 하면 AI가 **조치 카드**를 대화 안에 그린다(대상, 조치, 사유 분류와 메모). 사람이 카드에서 내용을 확인하고 "확인"을 눌러야 실행되며, 실행은 그 사람의 역할 권한으로 이루어진다(권한이 없으면 카드에 조치가 나오지 않는다). AI는 사유를 지어내지 않고 사람이 말한 것을 옮겨 적는다.
- **U14. 대화의 문맥과 파일.** 지금 열어 둔 대상이 자동으로 문맥이 된다(끌 수 있다). 화면의 다른 기록을 붙일 수 있다. 파일을 대화에 올리면 AI가 도구로 소명 절차에 넘긴다(어느 소명의 서류인지 정해지지 않으면 묻는다). 넘겨진 파일은 소명 화면에서 올린 것과 똑같이 글자 인식과 원본 대조를 거친다.
- **U15. AI 연결 방식.** 서버(Rust)는 `aisdk` 크레이트로 OpenAI를 부르고 도구를 실행한다. 화면으로는 AI SDK의 UI 메시지 스트림 형식으로 흘려보내고, 화면은 AI SDK(`ai` 7.x, `@ai-sdk/react`)의 대화 부품으로 받는다. `aisdk`에 내장된 변환기는 쓰지 않고 직접 옮긴다(`docs/spike/ai-stream.rs`에 검증한 코드). 조치 카드는 도구 호출 조각을 우리 부품으로 그려서 만든다.
- **U16. 내리는 순서.** 시간이 모자라면 대화 → 서류 글자 인식 → 가설 상신 → 모의 순으로 모의 처리로 내린다.
- **U17. 조치 카드는 도구 호출 조각을 우리 부품으로 그린다.** AI가 화면 구성 자체를 보내는 방식(A2UI)은 쓰지 않는다. 통제 업무에서 어떤 버튼이 나오는지는 우리가 고정한다.
- **디자인 하네스 문서**: `docs/design/`의 `tokens.md`(디자인 기준), `components.md`(부품 목록), `copy.md`(문구 기준), `sources.md`(출처 대응), `review.md`(검사 절차).

리서치 문서(`docs/research-ux.md`)는 우리 용어와 다른 말("묶음", "수용/기각", "종결")을 쓴다. 화면에는 쓰지 않는다.
