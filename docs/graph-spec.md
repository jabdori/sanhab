# 그래프 설계 스펙 (W07)

합의된 결정만 적는다. 용어는 `GLOSSARY.md`를 따른다. 기존 코드(`app/`)는 이 스펙과 다르다(지급 단위 판정, 관련자 관계 저장, 인지일을 등록일로 가정, 실행 중 AI 없음). 고칠지 다시 만들지는 미정.

## 확정된 결정

### D1. 그래프가 답해야 하는 질문
1. 이 지급은 어느 대리점들과 합산되며, 그 근거 경로는 무엇인가
2. 합산은 얼마이고 누가 승인해야 하는가
3. 정보가 정정되면 과거 승인과 지급 예정 건 중 어디까지 재검토해야 하는가
4. 이 작업이나 상태는 무엇 때문에 생겼는가
5. 승인 당시 회사는 무엇을 알고 있었는가
6. 이 판정은 어느 문서의 어느 조항, 어느 규칙의 몇 번째 버전에서 나왔는가

### D2. 심사
그룹 × 귀속월. 지급은 심사에 속한다. 그룹이 합쳐지거나 갈라질 때의 처리는 미정(열린 질문).

### D3. 관련자 표현은 세 층
- 사실: 대리점→식별자(주소, 계좌), 대리점→대표자(사람 노드)
- 규정 판정: 2개 이상 일치는 조회 시 계산. 사람이 확정하거나 소명으로 부정한 관계만 저장
- 정황: 사람↔사람 관계, 회수의 계좌 일치 등. 합산에 쓰지 않음

### D4. AI 역할
정황 탐지, 조사, 소명 처리, 변경 영향 설명. AI 산출물은 사람이 채택하기 전까지 합산과 승인권자 판정에 쓰이지 않는다.

### D5. 과거 승인에 대한 결론 수위
"합산 시 한도 초과, 재검토"까지만. 알고도 한 위반인지 몰랐던 오류인지는 회사의 인지일 증빙이 있을 때만 구분하고, 없으면 "구분 불가".

### D6. 규칙 버전
규칙 버전마다 시행 기간을 둔다. 모든 판정은 적용한 규칙 버전에 연결한다. 새 정책은 시행일 이후에만 적용하고, 과거 건에는 모의(영향 조회)만 허용한다.

### D7. 합산 기준 월
귀속월. **가정** — 규정 원문은 "월 지급액"이라고만 한다. 지급일 기준이면 지급 시기를 미뤄 한도를 피할 수 있다.

### D8. 정황이 걸린 건의 지급 처리
1. 정황은 지급을 막지 않는다.
2. 확인 작업(소명 요청)은 지급과 별개로 생기고, 소명이 올 때까지 열려 있다.
3. 심사 화면에 가설(정황이 사실일 때 그룹·합산·승인권자가 어떻게 달라지는지)을 함께 보여준다.
4. **가정** — 정황이 사실일 때 승인권자가 실제로 올라가는 건만 상위 승인권자에게 상신한다. 승인권자가 달라지지 않는 정황은 화면에 보여주기만 한다. 규정에 없는 절차이며, 하위 권한자가 "관련자가 아닐 것"이라고 스스로 판단해 전결하는 길을 막기 위해 추가했다.
5. 승인권자는 승인 / 보류 / 반려 중 하나를 고른다. 승인하면 "정황을 알고 승인함"을 기록한다. 보류분은 원 귀속월 합산에 남는다.
6. 이미 지급된 건은 건드리지 않는다. 소명 결과 관련자로 확정되면 재검토이 된다.

### D9. 대표자 일치
이름이 같으면 일치로 본다. 사람 노드는 이름마다 하나를 만들고 "동일인 미확인"으로 표시한다. 동명이인임이 소명으로 인정되면 사람 노드를 나눈다. 회사에는 동일인 여부를 증명할 자료가 없으므로 확인 책임은 대리점에 둔다.

### D10. 주소·계좌 일치
글자가 완전히 같을 때만 일치. 비슷한 표기는 정황으로만 다룬다.
- 현업 경험(유저): 주소가 같은 경우는 대개 도로명·건물번호까지만 같고 동·호수는 다르다. 동·호수까지 같은 경우는 드물며, 한 사무실을 나눠 쓴다는 뜻이므로 별도 확인이 필요하다.
- 원본 주소는 도로명·건물번호까지만 있다(동·호수 없음). 따라서 원본의 주소 일치는 "같은 건물"까지만 말해 준다.

### D11. 승인 후 그룹 구성이 바뀔 때
승인된 심사는 승인 당시 구성·합산·승인권자를 그대로 보존한다. 현재 구성으로 다시 계산한 결과를 옆에 붙여 비교한다.
- 합쳐져 한도를 넘으면: 기존 승인은 재검토. 아직 지급 전인 건은 새 구성으로 다시 심사.
- 갈라져 한도 아래가 되면: 기존 승인은 그대로 유효.

### D12. 소명 인정 권한과 역할 분담
내부 감시가 소명의 인정·불인정·보완을 결정한다. 증거를 모아 판단하는 일은 "돈이 규정대로 나가는지 확인하는 업무"의 범위 안이다. **가정** — 내부 감시는 영업 조직 밖에서 수행한다.

| 역할 | 하는 일 |
|---|---|
| 규칙(코드 계산) | 관련자 여부, 그룹, 합산, 승인권자, 재검토 표시 |
| AI | 정황 조사, 보고 작성, 소명 요청서 초안, 변경 영향 설명 |
| 내부 감시 | 정황의 채택·기각, 소명 인정 여부 결정, 추인 건의 확인·종결 |
| 영업지원 | 정산 접수, 소명 요청서 발송과 답변 접수, 한도 이하 전결 |
| 영업임원 | 한도 초과 승인·보류·반려, 재검토의 추인 |
| 회계·자금 | 지급 반영, 대사, 계좌 증빙 확인 협조 |

내부 감시는 정황·소명이 있는 건에만 관여하며 승인 흐름과 나란히 움직인다. 모든 지급의 관문이 아니다.

### D13. 소명 결과
인정(해당 일치를 관련자 근거에서 제외, 사유·증빙 기록) / 불인정(관련자 확정) / 보완(추가 요청, 그동안은 관련자로 본다).

### D14. 규칙 버전 적용 시점
귀속월 기준. **가정** — "새 규칙은 시행일이 속한 귀속월분부터 적용한다". 승인일 기준이면 승인을 미루거나 당겨 유리한 규칙을 고를 수 있다.

### D15. 인지일
원본에서 온 정보는 회사의 인지일을 "알 수 없음"으로 둔다. 시스템 운영 이후 들어온 변경(식별자 변경, 소명, 정황 채택)에만 인지일을 기록한다. 따라서 원본의 과거 승인은 모두 "구분 불가".

### D16. 합성 데이터
만들지 않는다. 정황 탐지와 재검토는 시연 중 조건 변경(주소 이전, 새 회수 입력)으로 보여준다.

### D17. 소명 증빙 목록
일치 종류별로 고정한다. **가정** — 규정에 없는 목록.
- 주소: 임대차계약서, 사업자등록증 → 동·호수가 다른가. 같으면 "추가 확인 필요"
- 계좌: 통장 사본, 예금주 확인서 → 예금주와 공유 사유
- 대표자: 생년월일을 확인할 수 있는 서류 → 동일인 여부

### D18. 정황의 채택과 기각
정황은 보고와 함께 내부 감시에 올라간다. 내부 감시가 소명 요청 또는 기각을 고른다. 영업지원은 정황을 기각할 수 없다.
기각은 "그 시점의 근거 기준"이다. 기각된 정황에 새 근거(새 회수, 식별자 변경 등)가 붙으면 이전 기각 사유와 함께 다시 올라온다. 근거가 그대로면 다시 올라오지 않는다. 새 근거가 붙었는지는 코드가 판단한다.

### D19. 합산에 넣는 지급
승인·미지급·보류는 넣고 반려만 뺀다. **가정** — 원본의 "미지급"은 승인 전 대기 상태로 해석한다.

### D20. 재검토의 후속 처리
1. 재검토이 되면 영업임원에게 추인 작업이 생긴다.
2. 영업임원은 추인(사유 기록) 또는 추가 소명 요청을 고른다.
3. 추인으로 끝나지 않는다. 내부 감시에 확인 작업이 넘어가고, 내부 감시가 확인해야 종결된다.
지급 회수 같은 조치는 시스템이 제안하지 않는다. **가정** — 규정에 없는 절차.

### D21. 장려금 비대상 대리점
그룹 구성원에 포함한다(합산에는 0원). 규정은 장려금 대상 여부를 관련자 조건으로 두지 않는다.

### D22. 계산과 AI의 경계
- 관련자 여부, 그룹, 합산, 승인권자, 재검토 여부는 모두 코드가 계산한다. AI는 이 값을 만들지도 고치지도 않는다.
- AI는 그래프 전체를 읽을 수 있다. 쓸 수 있는 것은 정황 제안, 소명 검토 의견, 설명문뿐이며 모두 "AI, 미채택"으로 표시된다.
- 식별자, 관련자 관계, 심사, 승인, 작업 상태는 AI가 고칠 수 없다. 권한 설정으로 강제한다.
- 대화에서 사람이 조치를 지시하면 AI는 실행하지 않고 조치 카드를 그린다. 사람이 확인을 눌러야 그 사람의 권한으로 실행된다(`docs/service-plan.md` U13).

### D23. 조사의 시작
새 사건(식별자 변경, 새 회수, 소명 답변 접수, 새 귀속월 심사 생성)이 들어오면 코드가 먼저 그룹·합산·재검토을 다시 계산하고 필요한 작업을 만든다. 그다음 AI가 그 결과를 설명하고 정황을 조사한다. 내부 감시가 요청할 때도 조사한다.

### D24. 보고의 근거 관리
- AI는 사실을 글로 옮겨 쓰지 않고 기록을 가리키기만 한다. 화면의 값(금액, 계좌, 날짜, 대리점 이름)은 코드가 원본에서 직접 꺼낸다.
- AI가 가리킨 기록이 실제로 있는지 코드가 검사한다. 없는 기록을 가리킨 보고는 내부 감시에 올라가지 않는다.
- AI가 글로 쓰는 것은 추정·의견·반론뿐이다.
- 제출 서류는 D26의 순서로 처리한다. **서류 원본은 항상 사용자에게 직접 보여준다.**

| 보고서의 칸 | 누가 채우나 | 맞는지 누가 보장하나 |
|---|---|---|
| 사실 | 코드(AI는 어떤 기록을 볼지 고르기만) | 코드 |
| 서류에서 읽은 글자와 위치 | 글자 인식 도구 | 내부 감시가 원본과 대조 |
| 서류 값의 정리(정규화) | AI | 내부 감시가 원문 조각과 대조 |
| 추정, 의견, 반론 | AI | 내부 감시가 판단 |

### D25. 내부 감시가 추인에 동의하지 않을 때
내부 감시는 승인을 뒤집지 못한다. 종결하지 않고 의견을 남기며 추가 소명 요청을 열 수 있다. 승인 권한은 규정상 영업임원에게 있다.

### D26. 서류 처리 순서
1. 대리점이 서류를 내고 영업지원이 접수한다.
2. 글자 인식 도구가 글자와 위치를 읽는다.
3. AI가 필요한 항목(호실, 예금주, 생년월일 등)에 해당하는 글자 조각을 가리키고, 그 값을 비교할 수 있는 형태로 정리(정규화)한다. 서류 양식은 다양하고 비정형 자료가 들어올 수 있기 때문이다.
4. 코드가 정리된 값을 대리점 등록 정보와 비교한다.
5. 내부 감시 화면에 원본, 읽은 원문 조각, AI가 정리한 값, 비교 결과를 나란히 보여준다. 내부 감시가 원본과 대조해 결정한다.

정리된 값은 "AI가 정리한 값"으로 표시하며 내부 감시의 결정을 돕는 데만 쓴다. 관련자 판정(D10의 완전 일치)에는 쓰지 않는다.

### D27. 시연용 서류
소명 서류는 과제 자료에 없으므로 시연으로 소수만 만든다. "시연용으로 만든 서류"로 표시한다. D16(가짜 대리점·지급을 만들지 않음)과 구분되는, 시연 중 넣는 새 사건이다.
- 호실이 다른 임대차계약서 → 인정
- 호실까지 같은 임대차계약서 → 추가 확인 필요
- 필요한 항목이 빠진 서류 → 보완

### D28. 글자 인식 도구와 AI 모델
- 글자 인식: 업스테이지 API(외부 호출). 실제 업무라면 서류에 개인정보가 있으므로 자체 운영이 맞다는 점을 설계 설명에 적는다.
- AI: OpenAI API. 기본 모델 `gpt-6.1-terra`, 환경변수로 바꿀 수 있게 한다(품질이 부족하면 `gpt-6.1-sol`).
- AI나 글자 인식이 멈춰도 계산·승인·지급은 그대로 진행된다. 보고만 "작성 대기"로 표시한다.

### D29. 정황을 찾는 주체
정해진 종류의 정황은 코드가 찾는다(빠짐없이 찾았음이 보장된다). AI는 찾아진 정황들을 엮어 조사하고 의미를 설명한다. 정해진 종류에 없는 신호를 AI가 발견하면 "기타"로 올린다.
정해진 종류: 회수의 계좌가 다른 대리점의 계좌와 같음 / 대표자 이름만 같음 / 한도 바로 아래 금액 / 지연(D30).

### D30. 식별자 변경의 소급과 늦은 인지
회사(서비스) 쪽에서 보는 날짜는 둘이다. **변경일**(사실이 실제로 바뀐 날)과 **인지일**(회사가 그 사실을 안 날). 대리점의 신고는 회사가 알게 되는 경로의 하나일 뿐이므로 "신고일"을 따로 두지 않는다. 인지에는 경로를 함께 기록한다: 신고 / 회수 / 소명 / 원본(인지일 미상).
식별자가 실제로 바뀐 날(변경일)부터 관련자로 본다. 변경일과 인지일 사이의 승인은 재검토이 되며 "당시에는 알 수 없었던 건"으로 구분된다.
변경일과 인지일의 차이가 큰 것 자체를 정황("지연")으로 잡는다. 승인권자를 바꾸는 정황이 아니므로 상신 대상은 아니다. **가정** — "늦다"의 기준 일수.

### D31. 소명 인정의 효력 범위
인정의 효력은 서류가 입증하는 기간을 따른다. 그 기간의 과거 귀속월도 다시 계산한다. 대리점의 식별자가 다시 바뀌면 인정은 효력을 잃고 새로 판정한다. 서류의 기간이 끝나면 재확인 작업이 생긴다.

### D32. 소명 미응답
요청에 기한을 둔다. 기한이 지나면 내부 감시에 미응답 작업이 생긴다. 답이 없는 동안에는 관련자로 계속 본다. 지급을 멈출지는 승인권자가 정한다. **가정** — 기한의 길이.

### D33. 승인 후 지급 전에 그룹이 바뀔 때
규정상 관련자가 되어 승인권자가 올라가면, 회계·자금의 지급 작업을 "재심사"로 돌리고 올바른 승인권자의 승인이 나면 다시 진행한다. 기존 승인은 기록으로 남기되 효력을 잃는다. 정황만으로는 이렇게 하지 않는다.

### D34. 내부 감시와 영업임원의 의견이 갈린 건
CEO에게 보고해 종결 여부를 정한다. **가정**. 설계 설명으로만 다루고 만들지 않는다.

### D41. 결정의 사유
사유는 결정한 사람의 것이며 AI가 지어내지 않는다(대화에서 사람이 말한 사유를 조치 카드에 옮겨 적는 것은 허용하고, 사람이 카드에서 확인한다). 결정한 사람을 잇는 선(13, 19, 28, 29번)에 사유와 시각을 함께 둔다. 이상이 없는 결정에는 강제하지 않는다.

|---|---|

필수인 쪽은 합산 대상을 줄이거나, 신호를 넘기거나, 건너뛴 절차를 추인하거나, 상대방이 이유를 알아야 하는 결정이다. 자주 쓰는 사유를 고르게 할지는 UX 기획에서 정한다.

### D42. 반려 이후
영업지원에 "재상신" 작업이 생긴다. 보완해 다시 올리면 대기로 돌아간다. 반려 기록과 사유는 남는다. 재상신해도 합산 대상과 승인권자는 그대로다.

### D43. 시스템의 시계
시스템의 오늘은 과제 기준일 2026-07-01에서 시작한다. 시연자가 날짜를 넘길 수 있다(예: 14일 넘기기 → 소명 기한이 지난 건에 미응답 작업 생성). 날짜 넘기기는 모의 처리다.

### D44. 필수 확장과 추가 확장
필수 확장: 유저가 만드는 제품 마션(Massion)에서 정리한 그래프 개념을 이 업무에 적용한 것. "마션이 구현한 것을 가져왔다"가 아니라 "마션의 개념을 적용했다"고 쓴다.

한 줄 요약: 변경과 결정을 노드로 남기고 근거·원인·결정자·버전을 선으로 이어서, 정보가 정정됐을 때 무엇이 영향받는지와 왜 이렇게 됐는지를 그래프로 답한다.

| 출처와 추론의 구분 | AI가 만든 것과 정황은 합산과 승인권자 계산에 들어가지 않는다 |
| 버전 고정 | 승인 당시의 구성과 규칙을 보존하고, 현재 계산을 옆에 붙여 재검토을 가린다 |
| 역방향 영향 추적 | 바뀐 식별자 선에서 출발해 영향받는 심사와 지급 작업을 찾는다 |
| 변경 이력 감사 그래프 | 어느 작업에서든 원인과 결정자를 거슬러 처음의 사건까지 닿는다 |

| 마션 감사 그래프의 선 | 우리 그래프의 선 |
|---|---|
| 근거 | 15(정황→근거), 18(소명→서류), 21(보고→가리킨 기록) |
| 의존 | 10(심사→대리점), 1~3(식별자 선) |
| 대체 | 27(규칙 버전→이전 버전) |
| 바로잡음 | 30(결정→이전 결정) |
| 버전 고정 | 11(심사→규칙 버전), 굳은 구성 |
| 원인 | 25(원인) |
| 결정자 | 13, 19, 28, 29(사유 포함) |

두 시간축(변경일과 인지일)은 마션의 개념이 아니라 이 업무에 맞춰 더한 것이다. 보고의 흐름은 마션 Growth의 제안·독립 평가·채택까지만 대응한다(효과 측정·롤백 없음).
추가 확장: 호실 단위 주소 확인(유저의 현업 경험), 두 시간축, 그 밖은 A04의 추가 확장 목록에 정리.

### D45. 대사와 정산
지급이 끝나면 회계·자금에 대사 작업이 생긴다. 회계가 은행 회신(지급 금액, 수취 계좌, 처리 결과)을 넣는다(모의 처리 — 원본에 은행 회신 자료가 없다). 코드가 승인 금액·등록 계좌와 맞춰 본다(실제 작동). 일치하면 심사에 "정산" 표시가 붙고, 흐름도의 "정산·소명 기록 보관"은 이 표시로 대신한다. 일치하지 않으면 정황으로 내부 감시에 올린다.
작업 종류에 "대사(회계·자금)"를, 심사의 표시에 "정산"를, 코드가 찾는 정황에 "지급 결과 불일치"를 더한다.

### D46. 개선 효과
원본의 실제 처리와 같은 자료에 이 시스템의 계산을 적용한 결과를 나란히 놓는다. 확인되는 숫자만 효과로 내세우고, 그 숫자가 기대는 가정을 함께 적는다.

| | 원본의 실제 처리 | 시스템 적용 시 |
|---|---|---|
| 2026년 1~5월 박상현 그룹(금강상사11·성일상사24·대륙상사37) | 15건 모두 영업지원 전결 | 5개 심사 모두 영업임원 승인 대상 |
| 합산 없이 전결로 승인된 금액 | 22,238,349원 | 0원 |

이 금액은 "승인권자가 달랐어야 하는 금액"이다. 잘못 지급된 금액이나 절감액이 아니다. 영업임원이 심사했더라도 승인했을 수 있다.

| 숫자가 기대는 가정 | 근거 | 가정이 달라지면 |
|---|---|---|
| 대표자 이름이 같으면 일치로 본다 | D9. 동일인 여부는 원본으로 확인 불가 | 세 대리점의 박상현이 서로 다른 사람으로 소명되면 그룹이 없어져 0건, 0원 |
| 주소·계좌는 지금 등록된 값이 1~5월에도 같았다 | 원본에 마스터 변경 이력이 없다 | 중간에 바뀌었다면 바뀐 달부터만 해당 |
| 한도 200만원이 1~5월에도 시행 중이었다 | 규정 문서에 시행일이 없다 | 한도가 달랐다면 달라짐 |
| 귀속월로 합산한다 | D7 | 지급일 기준으로 바꿔도 같다(각 귀속월분이 세 대리점 모두 같은 날 지급됨) |
| 관련자는 전이적으로 잇는다 | 과제문에 명시(가정 아님) | — |

처리 시간 단축 등은 측정 자료가 없어 효과로 쓰지 않는다.

### D47. 한 달 안에서 식별자가 바뀐 경우
그 귀속월에 하루라도 유효했던 식별자를 모두 본다. 3월 10일에 주소가 바뀌면 3월의 심사에서는 옛 주소와 새 주소 어느 쪽으로든 둘 이상 일치하면 관련자다. **가정** — 규정에 없는 해석. 월말이나 월초의 값만 보면 변경일을 맞추는 것으로 그 달의 합산을 피할 수 있다.

## 만드는 범위
원본 데이터나 시연 시나리오에 나오지 않는 예외는 새로 열지 않고 설계 설명 한 줄로 닫는다.

**실제 작동**
- 원본 적재, 그룹 계산, 귀속월 합산, 승인권자 결정
- 심사(그룹 × 귀속월)의 승인·보류·반려, 역할별 권한 강제
- 식별자 변경 입력(변경일·인지일) → 재계산 → 재검토 → 영업임원 추인 → 내부 감시 확인
- 승인 후 지급 전 그룹 변경 → 회계·자금 지급 작업 재심사
- 코드가 찾는 정황 네 종류, 가설 계산과 상신
- 기각된 정황이 새 근거로 다시 올라옴
- 보고(실제 호출, 가리킨 기록 검증)와 내부 감시의 채택·기각
- 소명 서류 처리(임대차계약서): 업로드 → 글자 인식 → AI 정리 → 비교 → 원본과 나란히 표시 → 내부 감시 결정 → 그룹 재계산
- 조항 → 규칙 버전 → 판정 연결, 경위
- 한도를 바꿔 보는 모의

**모의 처리**
- 대리점의 답변·서류 제출(시연자가 영업지원 화면에서 올림)
- 소명 요청서 발송(초안 작성 후 "발송됨" 표시)
- 소명 기한 경과("기한 경과" 입력)
- 지급 실행·대사(회계가 "지급 완료" 표시)

**설계 단계**
- 의견이 갈린 건의 CEO 보고, 사람↔사람 관계, 소명 인정 효력 만료와 재확인, AI 의견과 사람 결정의 차이를 모아 보는 화면, 통장 사본·생년월일 서류 처리, 새 정책 시행으로 규칙 버전이 넘어가는 장면, 글자 인식의 자체 운영

시간이 모자라면 서류 글자 인식 흐름 → 가설 상신 → 모의 순으로 모의 처리로 내린다.
