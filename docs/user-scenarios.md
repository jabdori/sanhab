# 사용자 시나리오 (초안)

`docs/graph-spec.md`의 결정을 실제 데이터로 따라가 본 것이다. 금액과 대리점은 모두 원본에서 가져왔다. 확정 전 초안이며, "미정"으로 표시한 곳은 결정이 필요하다.

## 등장하는 사람

| 역할 | 하는 일 |
|---|---|
| 영업지원 | 정산 접수, 한도 이하 전결, 소명 요청서 발송과 답변 접수, 대리점 정보 변경 입력 |
| 영업임원 | 한도 초과 건의 승인·보류·반려, 재검토 대상의 사후 승인 |
| 내부 감시 | 정황의 채택·기각, 소명 판단, 사후 승인 확인 |
| 회계·자금 | 지급 반영, 대사 |
| (AI) | 조사 보고 작성, 소명 요청서 초안, 서류 값 정리, 변경 설명 |
| (코드) | 관련자·합산액·승인권자·재검토 대상 계산, 정황 탐지, 작업 생성 |

## 출발 상태 (원본 그대로)
- 시스템의 오늘은 과제 기준일인 **2026년 7월 1일**이다(원본 README와 data_dictionary의 As-of).
- 2026년 1~5월분은 모두 영업지원팀이 승인했거나 반려했다.
- 6월분 40건이 심사를 기다린다.
- 코드가 계산한 결과: 박상현 그룹의 1~5월 승인 15건이 재검토 대상이다(매달 합산 400만원대, 모두 전결로 나감). 회사가 당시 알았는지는 "구분 불가".
- 코드가 찾은 정황: 성일상사24의 대금이 금강상사11·대륙상사37의 정산계좌로 들어옴 / 한라인상사34와 금강상사41의 대표자 이름만 같음 / 한도 바로 아래 금액 3건.

## 시나리오 1. 정상 — 아무 문제 없는 건 (전결)
**대성상사1의 6월분 988,932원**

| 순서 | 누가 | 무엇을 |
|---|---|---|
| 1 | 코드 | 대성상사1은 관련자가 없다. 합산액 988,932원, 승인권자는 영업지원 |
| 2 | 영업지원 | 심사 화면에서 근거(관련자 없음, 적용 조항과 규칙 버전)를 보고 승인. 사유는 쓰지 않아도 된다 |
| 3 | 코드 | 회계·자금에 지급 작업 생성 |
| 4 | 회계·자금 | 지급 완료 표시 (모의 처리). 대사 작업이 생긴다 |
| 5 | 회계·자금 | 은행 회신(금액, 수취 계좌, 처리 결과)을 입력 (모의 처리) |
| 6 | 코드 | 승인 금액·등록 정산계좌와 맞춰 본다. 일치하면 심사 단위에 "정산 완료" 표시. 일치하지 않으면 정황으로 내부 감시에 올린다 |

보여주는 것: 대부분의 건은 클릭 한 번으로 끝난다. 내부 감시와 AI는 관여하지 않는다.

## 시나리오 2. 정상 — 합산해서 임원에게 가는 건
**박상현 그룹의 6월분: 금강상사11 1,373,515 + 성일상사24 1,189,046 + 대륙상사37 1,325,536 = 3,888,097원**

| 순서 | 누가 | 무엇을 |
|---|---|---|
| 1 | 코드 | 세 대리점이 한 그룹(대표자·주소, 대표자·계좌). 합산액 388만원, 승인권자는 영업임원. 영업지원은 승인할 수 없다 |
| 2 | 영업지원 | 같은 건을 열어도 승인 버튼이 없다. "합산액이 한도를 넘어 영업임원 승인 대상"과 그 근거 경로가 보인다 |
| 3 | 영업임원 | 세 건을 한 심사 단위로 본다. 정황(통장 공유)이 함께 표시된다. 승인하며 사유를 쓴다(정황이 걸린 건이라 필수) |
| 4 | 코드 | 승인 당시의 구성·합산액·규칙 버전을 굳힌다. 회계·자금에 지급 작업 생성 |

보여주는 것: 이름이 다른 대리점이 합산되는 근거, 권한 강제, 정황은 지급을 막지 않고 승인권자가 알고 결정한다는 것.

## 시나리오 3. 과거 승인의 재검토
**박상현 그룹의 1~5월 승인 15건**

| 순서 | 누가 | 무엇을 |
|---|---|---|
| 1 | 코드 | 15건에 "재검토 대상" 표시. 영업임원에게 사후 검토 작업 생성 |
| 2 | AI | "왜 재검토 대상인가" 설명문 작성. 금액과 대리점은 기록을 가리키기만 한다 |
| 3 | 영업임원 | 사후 승인(사유 필수) 또는 추가 소명 요청 |
| 4 | 코드 | 사후 승인이면 내부 감시에 확인 작업 생성 |
| 5 | 내부 감시 | 확인 완료, 또는 종결 보류(사유 필수) |

보여주는 것: 과거 기록은 그대로 두고 현재 계산을 옆에 붙이는 것, "구분 불가", 내부 감시로 이어지는 마무리.

## 시나리오 4. 조건 변경 — 기각했던 정황이 주소 이전 신고로 되살아남
**한라인상사34가 "2월 1일부터 금강상사41과 같은 주소를 쓴다"고 7월 1일에 신고** (시연 입력)

준비: 내부 감시가 두 대리점의 "대표자 이름만 같음" 정황을 근거 부족으로 기각해 둔다(사유 필수). 영업지원이 한라인상사34의 6월분 1,353,657원을 전결 승인해 둔다(회계·자금 지급 대기).

| 순서 | 누가 | 무엇을 |
|---|---|---|
| 1 | 영업지원 | 주소 변경을 입력. 실제 변경일 2월 1일, 신고일 7월 1일 |
| 2 | 코드 | 두 대리점이 2월 1일부터 관련자(대표자·주소). 2월(2,218,474)과 3월(2,007,205)의 승인이 재검토 대상이 된다. 4월과 5월은 합쳐도 한도 이하라 그대로. 1월은 변경 전이라 무관. 승인 당시 회사는 몰랐으므로 "당시에는 알 수 없었던 건" |
| 3 | 코드 | 6월분은 합산 2,255,709원으로 승인권자가 영업임원으로 바뀐다. 조금 전의 전결 승인은 효력을 잃고, 회계·자금의 지급 작업이 "재심사 대기"가 된다 |
| 4 | 코드 | 기각했던 "이름만 같음" 정황에 새 근거가 붙어, 이전 기각 사유와 함께 내부 감시에 다시 올라온다. "늦은 신고" 정황도 잡힌다(실제 변경 후 5개월) |
| 5 | AI | 조사 보고 작성: 무엇이 왜 바뀌었는지, 두 정황을 함께 보면 어떤 의미인지 |
| 6 | 내부 감시 | 조사 보고를 보고 소명 요청 또는 기각(사유 필수). 보고의 채택·불채택을 남긴다 |
| 7 | 영업임원 | 6월분 심사, 2~3월분 사후 검토 |
| 8 | 누구든 | 어느 작업에서든 "왜 생겼나"를 누르면 주소 이전 신고까지 거슬러 올라간다 |

보여주는 것: 새 사건 하나가 과거 승인, 진행 중인 지급, 다른 부서의 작업, 넘어갔던 정황을 함께 바꾸는 것. 회사가 몰랐던 기간의 구분.

## 시나리오 5. 승인 거절과 정보 부족 — 보류, 증빙 부족, 보완 후 인정
**시나리오 4에 이어서. 한라인상사34·금강상사41의 6월분 2,255,709원** (서류는 시연용)

| 순서 | 누가 | 무엇을 |
|---|---|---|
| 1 | 영업임원 | 6월분을 보류한다(사유 필수). 지급 작업은 재심사 대기로 남는다 |
| 2 | 내부 감시 | 되살아난 정황과 늦은 신고를 보고 소명 요청을 정한다 |
| 3 | AI → 영업지원 | AI가 요청서 초안(주소 일치에 대한 요구 증빙 포함)을 쓰고, 영업지원이 발송 표시 (모의 처리) |
| 4 | 영업지원 | 대리점이 낸 서류를 올린다. 임대 목적물의 호실이 빠져 있다 |
| 5 | 글자 인식 → AI | 호실을 찾지 못함. 조사 보고의 "확인하지 못한 것"에 적는다 |
| 6 | 내부 감시 | 증빙 부족으로 결정(사유 필수: 무엇이 빠졌는지). 그동안 두 대리점은 관련자로 계속 본다 |
| 7 | 영업지원 | 보완된 임대차계약서를 올린다 |
| 8 | 글자 인식 → AI → 코드 | 글자와 위치를 읽고, AI가 임대 목적물 호실을 가리켜 정리하고, 코드가 금강상사41의 것과 비교한다. 호실이 다르다 |
| 9 | 내부 감시 | 원본 서류, 읽은 조각, 정리한 값, 비교 결과를 나란히 보고 인정(사유 필수) |
| 10 | 코드 | 한라인상사34의 주소 선이 "소명으로 제외됨". 두 대리점은 대표자만 일치하므로 다시 별개가 된다. 2~3월의 재검토 대상 표시가 풀리고, 6월분은 각각 전결 대상으로 돌아가 다시 심사된다 |

보여주는 것: 승인 거절 뒤의 다음 행동, 정보가 부족해도 흐름이 멈추지 않는 것, 호실 단위 확인이 판단을 바꾸는 것, 묶였다가 다시 풀리는 양방향의 변화.

## 시나리오 6. 소명으로 갈라져도 정황 때문에 상신되는 경우 (영상에는 넣지 않음)
**성일상사24가 "금강상사11과 같은 건물의 다른 호실"임을 입증** (서류는 시연용)

| 순서 | 누가 | 무엇을 |
|---|---|---|
| 1 | 내부 감시 | 주소 소명을 인정 |
| 2 | 코드 | 성일상사24는 대표자만 일치하므로 그룹에서 빠진다. 6월분은 {금강상사11, 대륙상사37} 2,699,051원과 성일상사24 1,189,046원으로 나뉜다 |
| 3 | 코드 | 통장 공유 정황이 남아 있다. 이 정황이 사실이면 성일상사24는 계좌 일치가 더해져 다시 합산 대상이다. 따라서 성일상사24의 건은 영업임원에게 상신된다 |

보여주는 것: 정황이 "사실이라면" 승인권자가 올라가는 건만 상신하는 규칙.

## 시나리오 7. 승인 거절 — 임원이 반려하거나 보류
**박상현 그룹의 6월분을 영업임원이 승인하지 않는 경우**

| 순서 | 누가 | 무엇을 |
|---|---|---|
| 1 | 영업임원 | 보류(소명이 올 때까지) 또는 반려. 사유 필수 |
| 2 | 코드 | 보류: 지급 작업이 생기지 않는다. 금액은 6월 합산에 그대로 남는다. 내부 감시에 정황 검토 작업이 이어진다 |
| 3 | 코드 | 반려: 영업지원에 "보완 후 재상신" 작업이 생긴다. 보완해 다시 올리면 심사 대기로 돌아간다. 반려 기록과 사유는 남고, 합산 대상과 승인권자는 그대로다 |

## 시나리오 8. 한도를 바꿔 보기 (가상 적용)
내부 감시 또는 영업임원이 한도를 150만원으로 바꿔 본다. 코드가 "현재 대비 승인권자가 달라지는 심사 단위 몇 건"을 보여준다. 실제 판정은 바뀌지 않는다.

## 공식 페이지의 시연 영상 요건
- 형식 MP4·MOV·WebM, 최대 1GB, 5분 이내 권장(넘는 부분도 심사), 1080p 권장
- 필수: 음성 해설 / 장면마다 실제 작동과 모의 처리를 말로 구분 / 빨리 감은 구간은 화면에 표시
- 장면 순서: ① 소개(30초) ② 정상 ③ 조건 변경 ④ 정보 부족 또는 승인 거절(조건 변경과 합쳐도 됨) ⑤ 필수 확장·다른 부서 영향이 앞 장면 어디서 쓰였는지 ⑥ 추가 확장(있을 때만)
- 설계 이유와 데이터 근거는 영상이 아니라 설계 설명 문항(필수 6, 선택 1, 문항당 1,000자)에 쓴다
