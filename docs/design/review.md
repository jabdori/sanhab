# 검사 절차 (디자인 하네스)

화면을 만든 쪽이 스스로 "됐다"고 하지 않는다. 아래 절차를 **실제로 돌리고** 그 결과(이미지·표)를 보고에 붙인다. **판정은 만든 쪽과 다른 에이전트가 한다**(만든 쪽은 판정을 위한 준비와 수정만).

## 순서 — 판정 → 보고 → 합의 → 수정
1. 검사 에이전트가 이 절차를 돌리고 결과 표를 낸다.
2. 만든 쪽은 결과 표를 고치기 **전에** 유저에게 그대로 보고하고, 고칠 방법(선택지 · 추천 · 이유)을 함께 낸다.
3. 유저와 합의한 것만 고친다. 고친 뒤 같은 절차를 다시 돌린다.

## 0. 목적 (모든 화면의 판단 기준)
- **W07의 질문에 답이 보이는가**: "이름이 다른 거래처가 사실은 관련된 곳일 때, 지급 합산과 승인은 어디서 확인하는가." 화면마다 관련 거래처 · 합산 · 한도 · 승인권자가 어디서 보이는지 한 줄로 적는다. 그 화면이 이 답에 기여하지 않으면 왜 있는지 적는다.
- **역할 분리**: 역할마다 자기 일만 보이고 할 수 있다(남의 조치 단추가 보이지 않는다, 권한이 없으면 승인권자가 보인다).
- **값의 출처**: 원본 값과 원본이 아닌 값(계산 · 가정 · 합성 · AI · 모의 · 예시)이 구분된다.
- **기록을 지우지 않는다**: 결정 · 사건 · 보고 · 대화에 삭제가 없다(D62).
- **처음 보는 사람**: 도메인 지식이 없어도 안내 · 도움말로 무엇을 하는 곳인지 알 수 있다.

## 1. 약속 대조
유저와 합의한 표 · 목록(예: 안내의 역할별 장면 표, 문구 초안)을 **기대값**으로 삼아 화면과 줄마다 대조한다. 합의 내용은 대화의 보고 · 결정 기록(`docs/graph-spec.md`, `docs/도움말.md` …)에서 가져온다. 한 줄이라도 다르면 어김(무엇이 다른지 적는다).

## 2. 말과 화면
화면의 문구(안내의 한 줄, 영역 제목, 빈 상태, AI 답)가 가리키는 것이 **그 화면에 실제로 있는가**.
- 가리킨 영역이 비어 있다(흰 칸만 밝힘), 다른 화면의 문구를 그대로 다시 썼다(AI 보고가 없는 기록에 "AI가 정리한 보고"), 다른 데이터를 다시 썼다(예시의 일치가 실제 데이터의 값) — 모두 어김.
- 숫자 · 이름이 화면 사이에서 서로 맞는가(타일 · 요약 · 표 · 대화의 답).
- **글마다 맡은 일이 있는가**(2026-11-15). 화면의 고정 글은 값의 이름, 사용자의 행동, 상태 가운데 하나를 맡는다. 시스템이 스스로를 설명하는 글, 안심 · 면책 문구(예: "판정은 사람", "참고용", "근거 기반"), 화면 구조나 다른 표지가 이미 말하는 것을 되풀이하는 글은 어김이다. 결정 문서(`docs/graph-spec.md`)에 적힌 문구라도 이 기준에 걸리면 지적한다(결정이 문구를 정당화하지 않는다). 도움말 · 안내의 설명 문장은 무엇을 하는 곳인지 알리는 일이라 허용하되, 그 안의 면책 · 안심 문장은 어김.
- **같은 화면에 이미 보이는 이름 · 제목을 다시 크게 쓰지 않는다**(2026-11-15, 대화 칸의 빈 상태에 기록 이름을 큰 글씨로 되풀이한 일). 템플릿에서 온 꼴이라도 그 화면에서 맡은 일이 없으면 어김이다.
- `labels.ts`의 허용 낱말 가운데 명사 한 단어가 아닌 것은 판정 때마다 하나씩 위 기준으로 남길 이유를 적는다(lint는 허용 목록을 믿으므로 뜻은 여기서 거른다).
옛 배치(`docs/ux-plan.md`의 다섯 칸 · 오른쪽 칸 순서)는 대체되었다. 이 절차는 그것을 검사하지 않는다.

## 2-1. 사람의 말 (개발용 표기 금지)
화면에 보이는 글은 처음 보는 사람이 읽는 말이어야 한다. 아래 개발용 표기가 화면(본문 · 머리 · 요약 · 표 · 툴팁 · 대화)에 보이면 **어김**이다.
- 파일 경로 · 확장자(`00_common/approval_authority_policy.md`, `m_agency_cv.csv`), 버전 코드(`v1`), 내부 식별자(`D-011`, `RB-00006`, 그래프 id `deposit:\`DP-00013\``, `acct:…`), 해시, 모델 이름(`fixture`, `gpt-…`), snake_case 낱말, 결정 번호(`D51`).
- 사람의 말로 바꾼다: 문서는 그 문서의 제목(`의사결정 권한`), 버전은 `버전 1`처럼 낱말(버전이 의미 있는 곳에서만), 대리점은 이름, 근거는 무엇인지(`회수 2026-03-13`).
- **예외**: 출처 설명 칸(`ui/Source`의 원본 · 가정 · AI 설명 — A05 §6의 원본 연결)은 확인하려는 사람을 위한 곳이라 파일 · 행 · 해시 · 모델 · 결정 번호를 둔다. 예외는 이 칸 하나.
- **기계 검사(판정 때마다)**: 화면마다 `document.body.innerText`를 받아 아래 정규식으로 훑고, 걸린 것을 결과 표에 적는다(출처 설명 칸을 열지 않은 상태에서 걸리면 어김).
  `\b[A-Z]{1,3}-\d{2,}\b` · `\bv\d+\b` · `\S+\.(md|csv|json)\b` · `[a-z_]+:\`` · `\b[0-9a-f]{12,}\b` · `fixture|gpt-[\w.-]+` · `\b[a-z]+_[a-z_]+\b` · `\bD\d{2}\b`
- **값 하나에 사실 하나**(2026-11-15 합의): 이름표-값 줄(MetadataList · 확인 창 · 조치 카드)의 값에 종류 · 이름 · 날짜 · 상태를 ` · `로 이어 넣지 않는다. `대상  심사 금강상사4 · 2026-06` → `종류 심사` / `대리점 금강상사4` / `귀속월 2026-06` / `상태 대기`. 상태는 기록 머리와 같은 Badge, 날짜는 고정폭 숫자. 여러 대상은 줄마다 하나.
- lint(`app/web/lint.mjs`)가 코드에서 막는 것: 버전 코드를 붙이는 `v${…}`, 파일 경로를 그리는 `.file`(출처 칸 `ui/Source.tsx`만 예외).

## 준비
- 문서: `tokens.md`, `components.md`, `copy.md`, `sources.md`, `docs/user-scenarios.md`
- 템플릿 렌더: components.md "화면 ↔ 템플릿"의 템플릿을 받아 neutral 테마로 1440 × 900에 띄워 찍는다(`astryx template <id> <임시 경로>`).
- 앱: 로컬 주소, 접속 패스워드. 검사 전에 시연 서랍의 초기화로 출발 상태를 만든다.
- 브라우저는 agent-browser를 **headless**로만 쓴다.

## 3. 템플릿과 나란히 (화면마다 — 바뀐 화면은 판정 때마다 반드시)
화면은 템플릿 코드에서 출발한다(components.md). 화면마다 **템플릿 코드와 우리 코드의 차이 목록**(부품 · 구조 · 스타일)을 만들어 components.md의 "템플릿에서 벗어난 곳"과 대조한다. 목록에 없는 차이는 어김. 이 절의 나란히 이미지와 차이 목록이 빠진 판정은 막힘(판정이 끝나지 않은 것으로 본다).
화면마다 `템플릿 | 우리` 한 장의 나란히 이미지를 만든다(같은 폭 1440). 흐리게 한 이미지(squint)도 한 장.
- 면: 흰 면 하나인가. 회색 면이 묶음 머리 밖에 있는가
- 경계: 영역이 Section · Divider · 표의 줄로 나뉘는가. 영역마다 Card가 있는가(Card soup — 막힘)
- 색: tokens.md "색" 표의 대응대로인가 — 상태(완료 · 진행 중 남색 · 멈춤 · 아님) · 범주 Token · 기록 종류 아이콘 · 결과 자리 CheckCircle이 템플릿만큼 보이는가(와이어프레임처럼 무채색이면 어김), 그 밖(출처 · 규칙 · 일치 종류 · AI가 쓴 글)에 색이 칠해졌는가(어김)
- 기본 상태: 대기 · 일치 · 접수 같은 기본 상태에 Badge가 달렸는가(달지 않는다 — `ui/status.ts`의 `DEFAULT`, `ui/Mark`의 `State`). 예외(보류 · 반려 · 재심사 · 누락 · 불일치 …)만 Badge
- 머리 칩 줄: 한 줄인가(상태 · 대상 · 핵심 하나둘). 날짜 · 기한 같은 값은 숫자 타일이나 본문으로
- 위계: 흐리게 봐도 제목 → 칩 줄 → 영역 제목 → 본문 순으로 읽히는가. 주 버튼(검정)이 묶음마다 하나인가
- 머리: 기록은 work-item-detail처럼 돌아가기 줄 · 제목 · 칩 줄인가. 작업은 table-grouped처럼 묶음 머리(접힘 · 건수)가 있는 표인가

## 4. is-my-code-good (Full product review)
`npx astryx docs is-my-code-good --full`의 루브릭을 화면마다 돌린다: App fit · Astryx components · Icons · Styling · Layout · Images · Code health. 항목마다 good / needs work / not inspected와 근거(파일:줄 또는 화면 파일). 확인하지 못한 것은 not inspected로 남긴다.
- 기계 검사(`cargo run -- check`는 DB에 시험 대화를 남기므로 **앱이 쓰지 않는 별도 DB**로 돌린다: `SURREAL_DB=w07check cargo run -- check`): `npm run build`(lint — 낱말 · 직접 값 · `style=` · Card 허용 파일 · 색 이름은 `ui/status.ts`만 — 와 tsc), `cargo test`, `cargo run -- check`.

## 5. 시나리오 (네 역할, 1280 · 1440)
`docs/user-scenarios.md`의 시나리오 1~6을 영업지원 · 영업임원 · 내부 감시 · 회계·자금으로 실제로 눌러 가며 따라간다(확인 창 · 일괄 승인 · 발송 · 서류 · 보완 · 인정 · 지급 · 모의 회신 · 변경 · 추인 · 모의). 단계마다 찍는다(`시나리오-단계-역할.png`).
- 숫자: 합산 · 승인권자 · 재검토가 되는 달이 시나리오에 적힌 대로인가
- 권한: 권한 없는 역할에 조치 버튼이 보이는가. 사유가 필수인 결정이 사유 없이 눌리는가
- 출처: 원본 값에 표지가 붙지 않았는가(조용한 행 번호). 원본이 아닌 값마다 표지가 있고 누르면 설명 칸이 열리는가
- 시연 분리: 날짜 넘기기 · 초기화 · 시연 서류 · 모의 회신이 시연 서랍에만 있는가. 서랍이 뒤를 막지 않는가
- 문구: `copy.md`(명사 한 단어, 조사 · 어미 없음, astryx 기본 영어 문구 없음)
- 끝나면 초기화하고 출발 상태로 돌아갔는지 작업 수로 확인한다.

## 6. 안내 (네 역할 × 1280 · 1440)
`docs/도움말.md`의 안내 표가 기대값이다. 역할마다 처음부터 끝까지 넘기며 단계마다 찍는다(`안내-역할-단계-폭.png`).
- 밝힌 영역: 한 줄이 말하는 것이 그 영역 안에 보이는가(2. 말과 화면)
- 한 줄: 제목(명사) + "여기가 무엇이고 무엇을 하는지"만인가. 도메인 설명은 도움말에
- 문제 장면: `다음`을 누르기 전과 뒤에 표의 변화가 실제로 일어나는가(숫자 · 막대 색 · 단추 · 상태)
- 예시: 예시 기록마다 `예시` 표지, 단추를 눌러도 실행되지 않음(작업 수 그대로), 끝나면 실제 목록으로 돌아옴, 대화 칸에 그 역할의 예시 대화
- 모양: 떠 있는 흰 카드 · 밝힌 영역의 링 · 꼬리가 그 영역을 가리킴 · 카드가 밝힌 영역을 가리지 않음 · 화면 밖으로 나가지 않음
- 도움말 창: 안내 다시 보기 · 판매장려금 · 이 역할의 일 · 낱말
